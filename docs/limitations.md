# Limitations

Every capability claim in this repository describes the current `develop` tree.
Where a feature is narrower than its name suggests, the boundary is stated here
rather than left for a reader to discover. Work that is not built yet lives in
[ROADMAP.md](../ROADMAP.md).

## Runtimes and hardware

- No publisher-operated, platform-complete signed `llama.cpp` or MLX artifact feed ships with this repository. ROCm, Vulkan, and DirectML are not advertised as maintained managed runtimes. The MLX service package can be built locally with `pnpm mlx:package` and installed from the Runtime Hub, but it installs only when signed by the pinned release key — there is no hosted feed serving one.
- The MLX video engine carries mlx-video pinned to a commit, because that project publishes no releases or tags and the name `mlx-video` on PyPI belongs to an unrelated package. Its open issue #40 reports black output from quantized Wan 2.2 checkpoints at some frame counts; the frame counts affected have not been mapped on reference hardware here.
- Hardware-fit estimates and runtime controls are implemented, but the ±15% memory matrix, clean-machine lifecycle checks, and the MLX release gate need maintained physical reference hardware. Edge-device profiles are still static heuristics; the Runtime Hub's Benchmark section measures throughput, time-to-first-token and peak memory on this machine, but those profiles do not yet read from it.
- `/v1/embeddings` produces real vectors only when the resolved runtime reaches an embeddings-capable backend (Ollama today); otherwise it returns an unsupported error rather than a fabricated vector. Native Ollama `/api/generate`, `/api/pull`, and `/api/show` are not implemented, and `/api/chat` returns a complete response rather than per-token streaming — real SSE streaming is OpenAI-compatible only.
- Vision is projector management and wire transport, not in-app vision chat: the main chat UI does not yet route attached images through that path, and the renderer cannot represent image blocks or reasoning content, so vision is never advertised as ready.
- Studio ships no model catalog, and its RAM floor is a check rather than a guarantee. `sd-server` covers three host targets, and the surface is hidden elsewhere rather than offered and failed at launch.

## Enforcement and isolation

- Every native process this app starts on the agent's behalf carries enforced tree bounds on memory, process count, wall clock and captured output, resolved from their class defaults and installed before the child execs: agent shells foreground and background on both desktop and CLI, browser sessions, post-edit verify commands, lifecycle hooks, and the disposable-copy sandbox run. All of them now carry a process-table row for their whole life, so a limit that fires on any of them is a typed breach in the processes ledger rather than a sentence in one command's result — and the row is a precondition rather than a report: a verify command, a hook or a sandbox run whose row cannot be written is reported as **not started** and never spawns, on the desktop and the CLI alike. The enforcement *level* differs by host and is reported rather than assumed: `monkey processes limits` and the Processes panel both name the backend and say `kernel` or `supervised`. macOS is always supervised, so a workload can exceed a memory bound for up to one 500 ms sampling interval before the tree is terminated; a kernel-held bound (cgroup v2, a Windows job) has no such window. A kernel-held bound is also *invisible to a comparison*: it refuses the work rather than letting a measurement pass the cap, so every owner asks the backend's own accounting before deciding why a workload ended, and a breach carries the counter that proved it. Other kinds are unchanged: a daemon job is bounded by its own recipe through the daemon's sampling watchdog, and the four WebView kinds by a six-hour configurable wall default. Daemon memory is opt-in; its seven-day wall bound is always present but deliberately loose.
- On Unix the generic kernel-held shell baseline still refuses only core dumps. File-size and descriptor ceilings are implemented and tested but unset because legitimate builds can produce large artifacts; CPU time is deliberately uncapped because it accumulates per core, and the relevant memory rlimit is a no-op on macOS — tree memory is held by the resource controller instead, not by `setrlimit`. The Windows job's 512-process and 4 GiB ceilings are now a *ceiling* rather than the policy: a process's effective limits are intersected with them, so a caller can tighten and can never widen. A macOS kernel-owned process tree remains genuinely absent, and what the supervisor does instead is narrower than it used to be. Ownership is sticky and durable: every process the workload is observed to own is recorded by `(pid, start-time)`, never removed, and written to the process ledger as it is discovered — beside the session the root led and, on a host whose start-time clock restarts with the machine, the boot those identities belong to. So a descendant that leaves the group, changes session or re-parents *after* it has been seen once stays owned, keeps counting against the budget it left, is reclaimed by the same termination, and is still reclaimable by the *next* app session if this one crashes: a restart takes the union of the persisted members, the recorded group and session, and the root, so an empty process group is not on its own evidence that the work is gone. Every persisted identity is re-checked against its recorded start time before anything is signalled, so a reused pid is treated as absent rather than killed. What is left is a descendant that both calls `setsid` **and** re-parents *before the supervisor has ever observed it*: no group, no session, no parent link, and nothing an unprivileged process can ask the kernel names the workload — and nothing to have persisted about it either. It keeps its Seatbelt filesystem and network confinement; what it escapes is the *lifetime* bound. Linux under a delegated cgroup has no such boundary — membership is inherited and cannot be left.
- Chat turns, subagents, Crew members, and side tasks default to a six-hour wall budget; Settings can choose 1–72 hours or disable it. A turn awaiting an unanswered permission prompt is indistinguishable from a working turn, which is why the default is deliberately loose. The budget is a floor, not a ceiling: a turn inside a 120-second shell command cannot notice it until the command returns, and paused time still counts.
- Every captured stream in the app is now drained concurrently and bounded as it arrives — the shell tool, verify commands, and monkey-cli, which used to collect both pipes whole and trim afterwards. The cap bounds app memory, not how many bytes the child may emit: a command that prints a terabyte still prints it, and the retained tail stays at the cap. A workload terminated for a limit loses the output collected up to that point, because the drain futures are dropped with the workload; the command did not finish, and reporting a partial capture as its output would read as if it had.
- Browser session sweeps cannot distinguish a tab you are still reading from one an agent abandoned, so the time limit applies to both. The disk limit is left out of the sweep. Unix records and reclaims the Chromium process group after an app crash; on Windows the job's `KILL_ON_JOB_CLOSE` ends the tree when the app process dies, so there is nothing left to reclaim rather than nothing able to.
- The opt-in Sandbox panel runs against a disposable workspace copy under macOS Seatbelt, Linux Landlock+seccomp, or a Windows AppContainer+job object; every run reports the level that actually applied, and platform capability is surfaced before launch and in Security Doctor. Agent foreground, background, and CLI shell tools use those same kernel backends as an always-on live-workspace boundary: the selected workspace and private runtime state are writable, filtered toolchain roots are read-only, PATH and inherited descriptors are narrowed, secrets are scrubbed from the environment, and opening host- or network-reachable socket endpoints — including loopback — is denied. Package downloads, dev servers, and socket-based local databases therefore do not work through shell tools; built-in web tools remain host-mediated under K5's per-run egress policy. Linux still permits local `socketpair(2)` IPC, which creates no host or network endpoint, but denies signal syscalls wholesale because classic seccomp cannot distinguish a child from the host; signal-based child control and process supervisors therefore fail there. The grant is the workspace namespace, so pre-existing hard links/FIFOs named there are workspace content, while linked-worktree Git metadata outside it is not granted. Windows keeps per-authority AppContainer profiles/ACEs pending a cleanup ledger. The Sandbox panel's run is bounded by the same resource controller as an agent shell and carries the same process-table lifecycle, so what owns its processes is the recorded owned set rather than the group alone; the residual macOS escape is the one described above, under the same Seatbelt policy. The disposable-copy Sandbox panel remains a separate opt-in workflow, not the evidence for agent-shell confinement.
- Paused desktop work does not survive a restart: a suspended desktop-owned row is reaped as `exited(lost)` rather than offering a Resume that cannot come back. Durable intent survives; durable execution does not. A workflow node has no cancellation of its own, a Crew member carries no edge to its coordinator, and a retried daemon job becomes a new process rather than inheriting the original's parent.
- A run killed for exceeding a budget is shown as cancelled in the run ledger, because `RunStatus` carries no limit status and adding a terminal status is a protocol compatibility change; the distinguishable exit is on the process record, which since V21 carries the limit, the configured value, the observed value, the backend and the enforcement level as typed columns rather than as prose.
- A restart that cannot establish what happened to a workload records `containment_lost` rather than `lost`, and the two are different findings: the second says the work ended, the first says only that this app stopped tracking it. The uncertain cases are a cgroup scope whose members would not die, a row carrying a pid with no start time or containment handle (written before migration V23), and a row naming a Linux cgroup being read on a host that is not Linux. Each names itself on the row and in the panel; none of them is reported as a clean exit.
- The output limit is a **retention** bound, not a termination bound: both pipes keep draining past it, the capture is front-truncated as bytes arrive, and a command that prints past it finishes normally. A command is never killed for being verbose. The panel and `monkey processes show` say that rather than showing a limit that looks like it would fire.
- A browser session's Chromium is bounded by two owners with disjoint resources, not by one: the resource controller holds the tree's memory and process count and reclaims the whole tree, and `browser_worker` keeps the session clock, the action budget and the profile-disk budget, which no controller can express. Every agent-controlled Windows workload is created suspended, assigned to its job, verified with `IsProcessInJob`, and only then resumed, so none of them runs an instruction before its containment holds — Chromium, the verify runner and the hook runner included, through `ResourceController::spawn_contained_*`. On Unix the equivalent ordering is the cgroup migration and the process group, both installed before `exec`. Agent shells and the disposable-copy sandbox run reach the same ordering through their own `CreateProcessW` call, which they need anyway because an AppContainer's capabilities cannot be carried by a `Command`.
- Inside a shared MCP transport, only the OAuth token fetch and keychain read run in the caller's task; the client library issues every actual request from its own worker, so those record neither a run nor a reason.

## Scope narrower than the name

- Memory Studio has two scopes and no pin, merge, or expiry. Approval chains are sequential and answered by the same desktop user. The connector catalog covers 5 of roughly 17 providers with pasted tokens rather than branded OAuth. Local App Builder's five templates are cosmetically similar. Inbox triage is read-only with no rules engine. Team Mode's RBAC is enforced at one defined point, and its audit trail attributes the exporter rather than the approver. Cross-Repo Intelligence uses text search, not a semantic index.
- Record & Replay's draft, review, and replay pipeline is real, including credential redaction, but recording means entering selectors in the workbench form rather than demonstrating an interaction.
- Acceptance criteria are pasted by hand, declaration names are a text match on changed lines rather than a resolved reference graph, binary and oversized files carry no citable hunks, hunk excerpts sent to the model are capped at 8 lines, and the coverage report lives in memory for the session. A diff hitting the 300-file or 200-hunk cap is reported as an incomplete view of itself, so a "not covered" verdict over one is shown as unproven.
- Release-gate eval state is desktop-local, so CLI and API-server workflow starts are not gated.
- Skill learning derives candidates from a run's durable events and your own turn text; it does not read the workspace's history, other sessions, or anything outside that run. Signal classification is a fixed rule set over those events plus a small phrase list for the explicit and correction signals, so a request phrased differently is not detected and a genuinely reusable procedure with no verification evidence is not proposed. Candidate evaluation really runs the candidate and a baseline in disposable copies of the workspace, executing their tool calls and the workspace's own verification commands — but that copy is bounded (4,000 files, 64 MB, skipping build and dependency directories), so a workspace larger than that, or one whose procedure depends on a skipped directory, records `unevaluated` rather than a pass. A candidate with no workspace on record, and one with no reachable model target, records `unevaluated` for the same reason. Each copy is rewound to the pre-task state from the originating turn's checkpoint, which covers every file this app's own write and edit tools changed; side effects a shell command had are not snapshotted by any checkpoint and so are not rewound either. Rather than evaluate a starting state it cannot show to be complete, the loop refuses: a run that used the shell records `unevaluated` and is never promotable on evidence, however good the procedure is. A run that only read the workspace needs no rewind at all, and a run that wrote files is rewound from its own checkpoint. Independently, for a task defined by a change of state, the evaluation verifies one untouched copy before any arm runs and records `unevaluated` if that copy already passes, which catches leftovers the rewind was never going to see. A run that changed files and whose checkpoint has since been pruned records `unevaluated`, because its starting state can no longer be reproduced. The CLI has no agent runtime of its own: `monkey skills learned evaluate` records `unevaluated` unless a runtime's case reports are supplied with `--report`, and reports supplied that way are recorded as `preflight`, which can never back an unattended promotion. Deduplication is deterministic (command, normalized description, sorted allowed tools, requirements, content digest, scope) with no semantic similarity pass, so two differently worded skills for the same procedure can coexist.
- The Red-Team Lab's containment column exercises the real boundary functions but cannot prove from a panel that the loop invokes them; that claim belongs to the CI test.
- Control Desktop keeps no local audit log or screenshots on the desktop side (the daemon-hosted remote path records them to the run ledger), does not block sensitive system dialogs, and matches its allowlist by application identity rather than verifying the frontmost window. The Windows and Linux/X11 input backends compile and their pure helper logic is tested, but neither has had a full runtime pass on real hardware — that remains a release gate.
- Browser verification uses disposable profiles. Persistent authenticated profiles, file transfer, clipboard, extensions, and general host control are out of scope. The in-app browser pane relies on Tauri's unstable multiwebview API.
- VS Code completion requires an installed Ollama model advertising `insert`; its latency and compile gate cannot be claimed without one.
- GitHub delivery needs local `git` and authenticated `gh`; hosted Actions need user-supplied provider credentials, and Ollama review needs a user-owned self-hosted runner.
- Local OCR, speech, meeting, and image paths require configured binaries, models, or endpoints. WER, diarization error rate, real-time factor, and image hardware behavior are not claimed until run against the documented external fixtures and hardware.
- Remote handoff requires a user-owned reachable network and valid TLS identity. There is no relay, account service, RBAC/SSO plane, or hosted GPU.
- The mobile companion pairs by QR code or pasted invitation, browses, approves, chats, launches saved workflows, and uploads captures, but browsing is online-only and push delivery needs an operator-selected provider. Physical-device, signing, and store-submission gates are unmet.
- A Talk utterance is named by the device and keyed on that name, so re-sending one lands on the run the first attempt made rather than starting a second. What is **not** built is a client that re-sends: when the socket drops, the shipped controller ends the session, releases the microphone and says so — the recording is not retained and nothing reconnects. The identity makes retransmission *safe*, it does not make it *automatic*, and automating it would mean minting a fresh signed ticket and silently re-opening a microphone after the runner dropped the session, which is a decision rather than a repair. A turn that was mid-answer when the socket closed is reported as lost so the person knows to say it again.
- Talk's wire protocol is at v2. v1 accepted a closing audio frame with no utterance id and v2 refuses one, so a page left open across an upgrade is refused once, by version, and told to reload; the service worker deliberately does not cache the controller so a reload gets the new client. The old behaviour is not kept as a compatibility fallback, because minting that identity on the runner is exactly what produced the duplicate-after-restart the version exists to close.
- Every path that reaches an agent from outside this machine — messaging channels, SMS and calls, paired devices, peers, Talk — runs on accounts, numbers, domains and hardware the operator supplies; this repository operates none of them. What that means per feature, and which of it is covered by automated tests versus needing a real account to verify, is in [Reaching an agent from outside this machine](messaging-devices-and-phones.md). Two boundaries are worth stating here: a provider that delivers by webhook needs a publicly reachable URL the operator exposes themselves (the listener binds loopback and opens nothing), and an extension-backed channel account cannot be shown to recognize its own outbound echo, because what a guest reports about a sender is the guest's word and the host cannot check it.
- A support bundle carries no message text, transcript, audio, key or credential, and replaces every identifier with a token salted per bundle. What it therefore cannot do is let two bundles from the same machine be joined, or let a reader recover which conversation an event belongs to from the document alone — that is the trade, and it is deliberate.

## Release

- Release hardening — clean-profile migrations, signed and notarized installers on every platform, accessibility and locale completion, performance budgets, dependency review, and penetration testing — remains a release gate rather than a completed claim. Signing is macOS-only, and the ten non-English locales each fall back to English for roughly a third of their keys.
- The in-app updater is real on all three desktop platforms: it checks in the background (8 seconds after launch, every 6 hours, and on window refocus when the last check is over an hour old), stages the bundle, then shows a relaunch card. macOS and Linux install underneath the running app; Windows defers its installer to the card click so an update cannot kill a turn mid-flight. Releases publish themselves: the workflow drafts while its six targets build, then flips the release once all of them have uploaded, so a failed target leaves a draft rather than shipping a partial release. Remaining limits: there is no manual check control, a failed check is silent, and Linux self-update covers the AppImage only.

## Dependencies this tree does not control

- Matrix runs on the maintained Rust `matrix-sdk`, whose SQLite store links `libsqlite3-sys`, and only one version of a `links` crate may exist in a binary — so **`rusqlite` is held at the version that store wants (0.37)** for the whole app rather than for one adapter. Nothing here needs 0.37 specifically; when upstream moves, this moves with it, and an attempt to bump it alone fails at resolution rather than silently. The alternative was hand-building the Client-Server protocol and a crypto store over our own `rusqlite` — key-loss risk, and a second partial Matrix implementation to maintain, in exchange for a version number.
- The same dependency brings `matrix-sdk-base`, and with it `decancer`, which adds `impl Add<_> for String`. That makes `String + &String` ambiguous **anywhere in the tree**; write `format!` instead. It is a compile error, never a silent behaviour change.
